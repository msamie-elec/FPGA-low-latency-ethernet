# Milestone M2A: Receive-only Ethernet UDP -> verified FPGA core -> USB UART

**Engineering state (2026-10-30):** new HDL and testbenches prepared; Python frame generation/reference checks and structural pin verification run locally. Icarus Verilog/Vivado are not installed in the authoring environment. **No claims of MII RTL simulation, Ethernet timing closure, or physical Ethernet board success yet.** This release must pass those gates on Windows before programming the board.

## Purpose and boundaries

This increment preserves the v0.3 UART-only design unchanged in its original sources. A **new top-level** demonstrates Ethernet reception and connects to the *same* `feed_pipeline.sv` used in the successfully verified physical UART application. The return path is deliberately USB-UART, **not Ethernet**. The next milestone adds Ethernet TX and a complete bi-directional IP stack.

```text
Windows PC 192.168.77.1/24
  | UDP broadcast 192.168.77.255:5000, 16-byte synthetic feed
  v
Arty A7 RJ45 -> DP83848J -> MII RX 25MHz domain
  | preamble / Ethernet / IPv4 / UDP narrow filter / FCS
  | single-entry CDC mailbox (toggle req/ack)
  v
100MHz Artix-7 core: feed_pipeline -> top_of_book -> response encoder
  | 14-byte 'R' report or 1-byte 'E'/'I'
  v
FTDI USB-UART -> Windows Python reference comparison (COM4)
```

The PHY receives a 25 MHz clock generated by dividing the onboard 100 MHz oscillator by four. The PHY is held in reset for about 10 ms after fabric reset. `eth_rx_clk` comes from the PHY on pin F15. RX logic is in **that** clock domain, not 100 MHz. The data bus is held stable across a request/acknowledge mailbox until the system domain finishes processing. Synchroniser flip-flops have `ASYNC_REG` attributes. These are architecture-level mitigations; a formal CDC and constraint review remains necessary.

## Supported traffic in v0.4A

* Link: 100 Mb/s MII, Ethernet PHY autonegotiates; link should indicate 100 Mb/s for the timing target.
* Destination MAC must be broadcast (`ff:ff:ff:ff:ff:ff`).
* EtherType `0x0800` (IPv4), fixed IPv4 header length 20 bytes (`0x45`), IPv4 total length exactly 44 (`0x002c`), UDP protocol `17`.
* UDP destination port **5000**, UDP length **24**, 16-byte application record at MAC byte offsets 42–57.
* Ethernet FCS checked by the reflected CRC32 residue `0xDEBB20E3` (calculated over destination MAC through received FCS, excluding preamble).
* A successful result returns on **USB-UART at 115200 8N1**. Same responses as v0.3 (`R` + sequence/bid/ask/signal, `I`, or `E`).
* Unsupported frames (ARP, IPv6, unicast, mismatched UDP port, bad FCS) are discarded with **no UART reply**. No Ethernet reply is transmitted. IP header and UDP checksums are **not validated in this milestone**; Windows supplies them for test traffic. IP fragments and variable IPv4 header lengths are unsupported.
* **Host sends one packet and waits for UART response.** There is one receive mailbox, no burst buffering or throughput claim. PHY frame errors reject a packet. These controls are intentionally restrictive for first bring-up.

## Verification order — Windows PowerShell in project root

1. Keep the existing v0.3 project/bitstream as the known-good fallback.
2. `python scripts/ethernet_vectors.py`
3. `python scripts/check_ethernet_m2a.py`
4. `python -m pytest -q tests`
5. `./scripts/run_ethernet_sim.ps1` (run as `& .\scripts\run_ethernet_sim.ps1`; if script execution is blocked, run the Icarus commands in the script manually). Require BOTH testbench `PASS` messages.
6. `& 'C:\AMDDesignTools\2025.2.1\Vivado\bin\vivado.bat' -mode batch -source scripts/build_ethernet_m2a.tcl`
7. Inspect `build/reports/ethernet_m2a/{timing_summary,methodology,cdc,utilization,power_estimate}.rpt`. **Do not program if critical DRC violations or unconstrained internal paths are found.** Board PHY signals require sign-off of physical MII timing and external clock waveform; the initial constraints are a bring-up set, not final sign-off.
8. Program `build/vivado_ethernet_m2a/ethernet_m2a.runs/impl_1/ethernet_uart_a7.bit` using Vivado Hardware Manager. Check board revision against the official Digilent master XDC.
9. Connect board RJ45 to a **dedicated wired Ethernet interface** on your Windows laptop or a switch. Keep the board USB attached for power/programming/UART. Modern laptop adapters generally support automatic MDI/MDI-X; use a switch if direct link fails.
10. Configure Windows Ethernet adapter IPv4 **192.168.77.1**, mask **255.255.255.0**, no gateway. Keep Wi-Fi independent. Check board RJ45 link LED and Windows adapter link status. Do **not** use internet-facing networks for experimental traffic.
11. Press/release BTN0 and test a single packet first:

```powershell
python scripts/ethernet_to_uart_test.py --com COM4 --pc-ip 192.168.77.1 --broadcast 192.168.77.255 --count 1
```

If it passes, run 10 packets:

```powershell
python scripts/ethernet_to_uart_test.py --com COM4 --pc-ip 192.168.77.1 --broadcast 192.168.77.255 --count 10
```

**LEDs:** LD4 = heartbeat; LD5 toggles for accepted Ethernet UDP frame; LD6 sticky rejected Ethernet frame (ARP/unmatched traffic can set it); LD7 toggles on a completed UART reply. The latter two are indicators only, not substitutes for host verification.

## What results mean

- LINK LED off -> check cable, Ethernet PHY reset/reference clock, negotiated link, PC adapter.
- Link on but LD5 never toggles -> investigate MII RX data/clock, UDP broadcast routing, packet framing, FCS, MAC filtering; capture traffic with Wireshark if needed.
- LD5 toggles but no UART response -> investigate mailbox CDC, core response, and USB-UART transmit. The v0.3 confirmed UART path is the reference.
- USB UART output matches expected for 10 packets -> M2A Ethernet receive/processing-on-board hardware smoke test **passed** (not throughput, stress or timing sign-off).
